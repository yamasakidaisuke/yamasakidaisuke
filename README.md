## ▍ How I Work — 手前の仕事

依頼はたいてい「なんかいい感じにしたい」から始まります。そこから動くものになるまで、だいたいこの順に降ろしていきます。

```text
「なんかいい感じにしたい」
   │
   ↓   何のためか、どうなったら成功かを決める（ここが一番時間かかる）
目的と判断基準
   │
   ↓   Webか、業務フローか、システムか。どこで解くかを選ぶ
設計
   │
   ↓   人とAIとツールが手を動かせる大きさに割る
タスク
   │
   ↓   公開して、運用に乗るまで見る
動いているもの
```

失敗するのはいつも1段目です。目的を詰めないまま作ると、きれいに動くのに誰も使わないものができあがる。何度かやりました。

<sub>なのでWebサイトも、納品して終わりの制作物としては見ていません。公開したあと誰がどう更新するかが決まっていないサイトは、半年で情報が古くなって放置されます。</sub>

<!-- ── PRINCIPLES（判断のものさし）──────────────────────── -->

## ▍ Principles — 迷ったときのものさし

- **70%で出す。** 100点になるまで待っている間、現場は困ったままです。出してから直すほうが早い
- **使われないものは作らない。** 設計がきれいでも、使われなければ0点
- **引き継げるかで判断する。** 見た目より、2年後に他の人が触れるかどうか
- **やりとりは見える場所でやる。** 口頭とDMだけで決まった話は、あとで誰も再現できません
- **ボールの所在をはっきりさせる。** 誰がいつ決めるのか決まっていない仕事は、だいたい止まります
- **工程は減らすほうを考える。** 承認を1つ足すのは簡単ですが、たいてい遅くなるだけでした
- 買うか自作するかは、そのつど決めています。自作が目的になっている時が一番危ないので、そこだけ気をつける
- ベストプラクティスより、いま目の前にあるコードと予算。正しくても今の現場で回らないなら、採用しません

AIは道具として見ています。責任は取ってくれないし、セキュリティも保証してくれない。出力をそのまま通さず、最後は自分で見て決める。Claude Code や Codex も、万能の1体というより、得意分野の違う作業者が何人かいる感覚に近いです。
